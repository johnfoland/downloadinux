# Chunk P0003-C03 — Browser/file registration and explicit refresh

**Goal:** Complete P0003 D2: users can discover supported selectors, register
browser accounts or Netscape files, and explicitly refresh a named source.
Successful operations publish immutable revisions through C01's transaction;
failures preserve the committed source/default. Source:
[issue #34](https://github.com/johnfoland/downloadinux/issues/34). Reference
#34 in the pull request; do not close it before D1–D5 are accepted.
This is preparatory: Stage 1 downloads/export/setup/doctor still use the shared
jar and ignore the source-store default until D4's coordinated cutover.

## Kickoff notes

The risky boundary is the real locked yt-dlp extraction/serialization API,
including its logger and warning paths; a write-only fake is not enough.
Reuse C01's parser/publication and C02's migration and summary fronts.
Capture the original source record before extraction; compare it under the
writer lock at publication, retaining the latest unrelated sources/default.
Generic registration/refresh never selects an account; the Firefox switch is D4.
Imports and file refresh must not load browser code, inspect profiles/keychains,
or call Docker. Browser extraction has no URL or downloader/extractor lifecycle.
Update public docs per unit, preserving the Stage 1/preparatory distinction.

**Review-checklist entries this chunk is likely to trip:**

- `review-checklist §1`: filesystem/dependency failures must reach safe CLI exit 1.
- `review-checklist §2`: extraction, logger, and serialization doubles must match the real adapter.
- `review-checklist §3`: unexpected third-party failures must not leak raw diagnostics.
- `review-checklist §4`: serialization/normalization must not silently lose credentials.

**Read first:** target design *Named cookie sources* §§1, 2, 5, plus §4's
source/user-agent independence; *Host application* and *Configuration and paths*;
implementation plan *Stage 2* and *Validation throughout the stages*;
DEC-28 to DEC-30, DEC-32/DEC-33, DEC-24/DEC-27. Numbered § citations below
refer to *Named cookie sources*.

**Preconditions:** C02 accepted/integrated through PR #40; P0003 active;
Docker running for `just check`. Fixtures use synthetic jars/profiles only,
without installed browsers, real keychains/credentials, VPN, or live sites.

## Units

### P0003-C03-a — Browser adapter and supported-selector front

**Build:**

- Add an injectable host adapter for direct Firefox/Chrome/Chromium cookie
  extraction and serialization (§2, DEC-29/DEC-30). Validate and bound the
  current yt-dlp release actually exercised, add it to host runtime dependencies,
  update `uv.lock`, and record its version/API evidence. Load the browser adapter
  only for browser operations; source readers, import, and downloads remain
  independent of profile/keychain access. Do not add host media dependencies.
- Implement shared selector validation/normalization for macOS/Linux (§1–§2):
  profile names stay names; path-like/leading-tilde profiles become absolute
  without resolving symlinks. Firefox supports optional container (`none`
  means outside containers, absent means all); Chromium browsers support only
  the locked adapter's Linux keyrings. Refuse unsupported browser IDs and
  platform/browser/selector combinations as usage errors before extraction.
- Consume all third-party diagnostics internally. Any reported extraction or
  decryption warning/error, unsupported schema, or thrown extraction/serialization
  exception fails conservatively with safe browser/selector context and remedy
  (including Netscape import), never raw diagnostics/tracebacks/cookie data.
  Clean empty output succeeds; parsed/serialized material retains the shared
  parser's session/expired, domain, secure, and available HttpOnly semantics.
- Expose shared `cookies browsers [--json]` (§2, §5) with exact platform and
  Firefox/Chrome/Chromium capability schema/order. It neither probes installation
  nor reads/migrates the source store. Document its limits, locked version,
  Linux keyring prerequisites, and imports as the browser-independent alternative.
  Update *Host application*'s Stage 1-only runtime-dependency description when
  adding the dependency; mark new browser support as implemented preparation.

**Tests:** Both platform support reports and selector matrix; profiles with
spaces, names, relative/absolute/tilde paths, symlink spelling, and Firefox
containers including `none`; actual locked API signature/logger/serialization
contracts. Drive the adapter against synthetic profile data through the real
cookie extraction entry point for a credential-free case, and use controlled
decryption/profile fixtures for platform-specific paths. Block network and
downloader/extractor entry points. Real jar serialization tests cover empty,
session, expired, secure, domain normalization, and available HttpOnly records;
assert no silent record loss (`review-checklist §4`). Capture warning/error/debug
canaries, including warning-before-valid-output and exception/serialization
failures; no raw text escapes. Doubles use the real API/logger signatures and
output lifecycle (`review-checklist §2–§3`). Browser support listing never calls
migration/extraction; non-browser operations never load the browser adapter.

**Done when:** a locked install exposes the exact browser support report and
the direct adapter returns strictly validated material or a safe operation
error, with real third-party boundary evidence. Focused tests and `just check`
pass without host browser/keychain/site access.

### P0003-C03-b — File/browser registration and explicit replacement

**Build:**

- Add shared operations and thin CLI fronts for `cookies import NAME FILE
  [--replace]` and `cookies add-browser NAME --browser BROWSER [--profile
  PROFILE] [--keyring KEYRING] [--container CONTAINER] [--replace]` (§1–§2,
  §5). Preserve nested global flags and exit 2 for invalid names/selectors
  before cookie operations. Valid source access calls C02's migration first;
  capture expected absence/original record before import/extraction.
- Normalize file origins with tilde expansion and absolute paths against the
  invoking directory, without resolving symlinks (§1). Read/parse external
  files with C01's real parser, or use unit a's browser adapter. Publish only
  valid complete material with a fresh revision/UTC timestamp via the existing
  locked writer. An existing ID refuses without `--replace`; explicit replacement
  may change kind/origin while retaining its ID and current default selection.
  Registration never implicitly selects, including the first source (§1–§2).
- Preserve unrelated sources and the latest default from the locked reread;
  changed original records refuse with retry guidance. Do not chmod/overwrite
  external imports/profiles or old/canonical jars. Retain old revisions and
  permitted unreferenced/reservation residue per §1 and DEC-27. Reuse the
  existing human inspection renderer and shared summary contract for success
  (§2), with new-source metadata/counts and no individual cookie names/values.
- Update README/cookie README, command reference/layout, and planning status
  with runnable file/browser registration and explicit default examples. Make
  clear import needs no browser, new registration keeps anonymous or the
  existing default, and current downloads still use the Stage 1 jar (§5).

**Tests:** Public CLI and shared-operation paths: file imports with no browser
adapter import/access, full selector forwarding, first registration/default
preservation, duplicate refusal, file↔browser/origin replacement, and exact
success summary parity with inspection. Pin origin normalization, retained
external bytes/modes, immutable old revisions, fresh IDs/timestamps even for
identical data, 0700/0600 published modes, empty jars and parser edge cases.
After successful one-time migration, failed registration preserves that
committed baseline; invalid legacy still publishes nothing. Exercise bad files,
denied reads, damaged stores, browser warnings/errors, and publication/cleanup
faults through `cli.main` for safe path/source errors and exit 1 (§1–§3 of the
review checklist). Real process barriers prove two registrations of the same
absent ID cannot both win and replacement cannot overwrite a record changed
during extraction; unrelated registrations/default changes survive. Reuse the
real writer oracle, with no copied publication implementation. Global flags
work at every parser level with spaces/custom/XDG paths; no credentials/Docker/UA
operation or tracked config write is introduced.

**Done when:** both registration routes atomically create/replace managed
sources with secret-free inspection summaries and explicit-only default
selection; failure/concurrency/permission contracts hold, current-user docs
describe the new surface, and focused tests/full `just check` pass.

### P0003-C03-c — Explicit refresh and D2 integration evidence

**Build:**

- Add shared `cookies refresh NAME` and thin CLI front (§1–§2, §5; DEC-29).
  Migrate first, reject unknown valid IDs as operation errors, and reread the
  registered file/browser origin explicitly using the same import/adapter
  paths as registration. Capture the original record before extraction and
  publish via C01's comparison/transaction, with no implicit account switch.
  Success always produces a fresh immutable revision/time and the shared
  inspection summary; failure preserves prior committed state/material/default.
- Document explicit refresh, missing origins leaving the last managed copy
  inspectable, browser selector/keyring remedies, and source/UA independence.
  Gather every D2 *Done when* item from project §5 into the report with named
  tests/gate evidence. Update implementation status for D2 while leaving
  private execution and all D4 routes pending; #34 remains open.

**Tests:** File origin changes/deletion, valid empty refresh, browser-origin
selector reuse, failed extraction/decryption/serialization/parsing/publication,
and unchanged old material/default/UA/settings. Drive safe exit-1/exit-2 errors
and matching human success summaries through CLI; nested flags remain valid.
Independent-process barriers prove competing refreshes of one original record
cannot both publish, replacement during extraction refuses stale refresh, and
unrelated source/default changes are retained. Compare registration and refresh
validation/publication semantics against the same fixtures/real writer, not
two independent fakes. Pin existing Stage 1 download/export/setup/doctor routes
still ignoring sources/default and retaining their implemented behavior.
Verify locked installs run import/list/inspect/file refresh without installed
browsers/keychain prerequisites, and synthetic platform/browser fixtures cover
D2's acceptance without a site request.

**Done when:** refresh re-reads the stored origin safely, all D2 evidence is
recorded with passing focused tests and all seven `just check` steps, and docs
accurately describe implemented registration/refresh plus pending execution.
