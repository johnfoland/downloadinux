# Chunk P0001-C03 — Container commands, login on set-token, and D2's close

**Source:** project [P0001](../projects/P0001-portable-config.md), delivery
item D2 (the rest), plus findings 1 and 2 of the P0001-C02 review.
Authority: [target design](../target-design.md) *Host application*
("Commands in the container, pinned for P0001-C03", and the C02 "Docker
invocation" list it builds on), *Migration* ("Pinned for P0001-C03,
completing D2's wrappers"); DEC-11, DEC-16.

**Goal:** every D2 command exists. `dlx shell`, `dlx vpn …`, and
`dlx servers …` reach the configured project's container through the
computed invocation, `dlx config set-token` logs a running VPN container in
without the token ever touching a host argument list, and the `shell`,
`vpn`, `servers`, and `status` recipes are wrappers over them. The NordVPN
server ranking moves into the package, so `scripts/servers.py` and its gate
step go. `just doctor` stops depending on `.env`, and a failed settings
write names the settings file. With the two-project manual check recorded,
D2 is done and D3 (presets) is next.

## Kickoff notes

- **Unit b's runner change is the shape everything else uses.** `servers`
  and the running check need a command's stdout; extend the injectable
  runner (or add a capturing sibling) so tests still start no process. Keep
  `compose --`, `shell`, and `vpn` uncaptured: they are interactive.
- **The token** goes to `exec` only as `-e NORDVPN_TOKEN` with the value in
  the process environment (verified: Compose v5 reads it from there). Tests
  assert the fake token is in no argv, and in no environment when the VPN is
  off or the container is stopped (nothing runs then).
- **`servers` is a move, not a rewrite**: capture today's script output on a
  fixture first, then delete the script; the test holds the new code to that
  capture. `curl -g` matters: without it curl reads `[country_id]` as a glob.
- **The gate shrinks to seven steps** (`3/8` goes with `scripts/servers.py`).
  Relabel `N/7` and update AGENTS.md *Commands*; CI runs `just check`, so
  the workflow does not change.

**Review-checklist entries this chunk is likely to trip:**
`review-checklist §1`: the new `exec` and capture paths are subprocess calls;
a missing `docker` must still end as `downloadinux: error:`, exit 1.
`review-checklist §2`: every fake runner and every faked failure here must
fail the way the real one does (a capture of a stopped container's `ps` is
empty output with status 0, not an exception).

### P0001-C03-b — `shell`, `vpn`, `servers`, and their wrappers
**Build:**
- Container `exec` and the capture runner per "Commands in the container,
  pinned for P0001-C03": `exec -u dl downloadinux <argv>` through the
  computed invocation, `-T` only when captured; a "container is running"
  helper (`ps --status running --quiet downloadinux`, non-empty output)
  for unit c.
- `shell`: `zsh`, exit with its status.
- `vpn [args…]`: the container's `vpn` helper with `args` (`status` when
  none), exit with its status; with `vpn.enabled` false, exit 1 naming
  `vpn.enabled` and run nothing (DEC-16). `argparse.REMAINDER`, so
  `dlx vpn on United_States New_York` passes through unchanged.
- `servers [city] [country]`: the `curl -sg --max-time 40 <url>` argv as
  pinned, captured, ranked in a package module (suggested
  `src/downloadinux/servers.py`), output as today; a non-zero fetch or a
  non-JSON body exits 1 with the pinned message; runs with the VPN on or
  off. Then delete `scripts/servers.py`.
- Gate: remove step 3 (the `servers.py` compile) and relabel `N/7`;
  AGENTS.md *Commands* lists the seven steps.
- Recipes per *Migration*, "Pinned for P0001-C03": `shell`, `vpn`,
  `servers` run the CLI commands; `status` runs `{{compose}} ps` then
  `uv run downloadinux vpn status || true`. Recipe comments (menu text)
  stay accurate. The `servers` recipe keeps its own header and trailing
  hint lines (the script never printed them).
- README.md: the host CLI section gains `shell`, `vpn`, `servers`; the
  *Layout* tree drops `scripts/servers.py` and shows the new module.
**Tests:** with fake runners: `shell` runs `… exec -u dl downloadinux zsh`
(no `-T`) and returns its status; `vpn` with no arguments runs `vpn status`,
with `on United_States New_York` passes the three words as three arguments,
and with `vpn.enabled=false` exits 1 naming `vpn.enabled` with no runner

`scripts/servers.py` before its deletion (one city with servers, one
without, both committed as fixtures); a non-zero fetch status and a
non-JSON body each exit 1 with the message; `servers` runs with VPN off.
Missing `docker` on `shell` exits 1 (`review-checklist §1`).
**Done when:** the tests pass, `just check` passes with seven steps, and

### P0001-C03-c — Login on `set-token`, and D2's close
**Build:**
- `config set-token` per the pinned list and DEC-16: store first; with the
  VPN enabled and the container running, the login through
  `exec -T -u dl -e NORDVPN_TOKEN downloadinux sh -c 'nordvpn login --token
  "$NORDVPN_TOKEN"'` with the token only in that process's environment,
  output discarded; `Logged in.`, then `nordvpn connect` with `vpn.server`'s
  words when `vpn.autoconnect` is true (a failed connect warns, exit 0); a
  refused login exits 1 with the pinned message; stopped container or VPN
  off: the pinned messages, exit 0, no login attempted.
- Docs: D2 in the project file marked implemented; *Host application*,
  *VPN mode*, and *Migration* status lines say every D2 command is
  implemented; README describes `just token`'s login and the `vpn`
  command's refusal with the VPN off.
**Tests:** with fake runners: VPN on and running: the login argv is exactly
the pinned one, `NORDVPN_TOKEN` equals the fake token in that call's
environment, and the fake token appears in no argv of any call; autoconnect
true with `vpn.server="United_States New_York"` runs `nordvpn connect
United_States New_York` as two arguments, empty server runs it with none;
autoconnect false runs no connect; a refused login exits 1 with the token
still stored; a failed connect exits 0. Container stopped (capture empty,
status 0): no login call, exit 0, message names `dlx up`. VPN off: no
runner call at all, exit 0. No call ever runs `nordvpn logout` (DEC-16).
**Done when:** the tests pass, the gate passes, and by hand, recorded in the
report: two configs with different `container.project` and downloads
directories (VPN off) are up side by side (`docker ps` shows both), each
`dlx --config … compose -- exec -u dl downloadinux ls /downloads` lists its
own downloads directory, and both come down cleanly (D2 *Done when*); with an imported VPN-on config, `just token`
against the running container prints `Logged in.` (or, if already logged in,
the refusal and `dlx vpn logout` hint), and `just vpn status`, `just
servers`, and `just status` work. No token in any output or record.

## Notes for the executor

- The capture runner's fake for "container stopped" returns status 0 and
  empty output: that is what `ps --status running --quiet` does for a
  stopped service. A stopped *project* also returns 0 and empty.
- `vpn login <token>` through `dlx vpn` still puts a token on an argv; that
  is the user's explicit choice and stays as is. README should point at
  `just token` instead.
- `servers` today parses on the host with `python3`; in the package it is
  ordinary code under the CLI's Python, so no `python3` subprocess.
