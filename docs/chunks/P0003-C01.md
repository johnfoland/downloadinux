# Chunk P0003-C01 — Strict cookie parser and atomic source-store foundation

**Goal:** Build the reusable parser, secret-free summaries, strict registry
reader, and atomic host writer that named cookie sources require. This is the
first part of P0003 D1, sourced from [issue #34](https://github.com/johnfoland/downloadinux/issues/34).
It establishes the storage boundary before another chunk adds automatic legacy
migration and the public `list`/`inspect`/`default` fronts. Existing Stage 1
commands continue unchanged; this chunk exposes no new user command. Reference
#34 in the pull request, but do not close it: D1–D5 together resolve that issue.

## Kickoff notes

Read target design *Named cookie sources* §1–§2 closely: a registry replacement
commits the complete change; retained revisions make lock-free readers safe.
Use the real `MozillaCookieJar`, retaining session and expired records, with
strict validation around its permissive/error-prone edges. Serialization must
preserve meaning, including empty names/values and HttpOnly, rather than bytes.
Keep parser/reader imports independent of host settings and browser packages
so D3 can reuse them in the image. Reuse `files.write_atomic`; do not duplicate
the DEC-24/DEC-27 fallback. Migration and CLI error rendering follow this chunk;
no current download, setup, export, or doctor route reads this store yet.

**Review-checklist entries this chunk is likely to trip:**

- `review-checklist §1`: filesystem failures need path-bearing operation errors.
- `review-checklist §2`: injected publication/cleanup failures must match real OS exceptions.
- `review-checklist §3`: malformed input must never leak a library traceback or cookie content.

**Read first:** target design *Named cookie sources* §1 (source store), §2
(parser, metadata, summaries, error classes), and §5 (migration and coordinated
cutover boundary); *Host application*, package/error contract and portable
no-clobber writes; *Configuration and paths*; implementation plan *Stage 2*
and *Validation throughout the stages*; DEC-24, DEC-27, DEC-28, DEC-30, and
DEC-31's retained-revision requirement. Numbered § references here refer to the
five subsections within *Named cookie sources*.

**Preconditions:** P0003 is active, with no earlier P0003 chunk; P0002 is
accepted and integrated. Start from current `master`; Docker must be running
for `just check`. Fixtures use only temporary stores and synthetic cookies,
with no browser, keychain, VPN, real credentials, or live-site requests.

## Units

### P0003-C01-a — Shared Netscape parser, serializer, and safe summaries

**Build:**

- Add a reusable module under `src/downloadinux/` for strict Netscape parsing
  and serialization around `MozillaCookieJar`, per *Named cookie sources* §2
  and DEC-30. Accept UTF-8 with optional leading BOM, LF/CRLF, the specified
  cookie header, blank/comment lines, and HttpOnly records. Validate all seven
  fields and domain/subdomain consistency before the library can drop or
  overwrite a record. Normalize empty/zero expiry to session semantics; retain
  expired records, secure/HttpOnly flags, and empty names/values. Reject
  duplicate domain/path/name keys. A header-only jar is valid.
- Provide non-secret count/domain summaries using an injectable inspection
  clock. Implement the exact partition, lexical domain order, and recognized
  session-cookie presence of §2. Keep cookie records separate from public
  summary objects; errors report path, line, and field without input content
  or raw parser exceptions. Path-bearing OS failures retain the established
  operation-error contract (*Host application*; review-checklist §1 and §3).

**Tests:** Synthetic fixtures cover every accepted format and validation
rule, missing/wrong header, invalid UTF-8, wrong field count, invalid flags,
domain/subdomain mismatch, invalid domain/path/expiry, duplicate keys, session
and expired retention, and empty names/values. Round-trip through the shared
serializer and the real `MozillaCookieJar` (with session/expired retention)
and assert semantic equality, including HttpOnly and secure flags. At an
injected clock, test expiry equality, the four-count partition, lexical
domains, Instagram/YouTube exact and dot-suffix recognition, lookalike domains,
and recognized-cookie presence despite expiry. Canary names/values never
appear in summary serialization or error text. Exercise an actual failing
file read and library parse failures (review-checklist §1–§3).

**Done when:** Parsing/serialization preserve all specified semantics; every
malformed fixture fails safely with path/line/field, and summaries implement
§2 without names, values, or authentication claims. The unit's focused tests
and the unchanged full `just check` gate pass.

### P0003-C01-b — Strict immutable-revision reader and metadata contracts

**Build:**

- Add a reusable source-store module and typed metadata representation for
  *Named cookie sources* §1's exact version-1 registry, stable source names,
  random revision shape, UTC timestamps, file/browser record fields, nullable
  default, and canonical revision paths. Validate exact types, unknown fields,
  supported browser IDs, kind-specific fields, and registered defaults; never
  silently repair a damaged registry or choose anonymous after an error.
- Read an atomic registry snapshot without taking the host writer lock;
  validate referenced revisions and load requested material through unit a's
  parser. Keep missing-registry handling distinguishable from a valid empty
  registry so the later host migration operation can act under the lock.
  The low-level reader itself performs no migration, directory creation, or
  registry publication (§1 and §5's host/container separation).
- Implement pure source/list/inspection metadata assembly with exactly §2's
  public JSON fields and lexical ordering. A file source's absent external
  origin does not invalidate its existing managed revision (§1). Accept the
  cookie root explicitly; do not load effective settings, credentials,
  browsers, or Docker in parser/reader imports. Keep host writing separate.

**Tests:** Validate the example schema for both kinds, anonymous/empty stores,
the 1/64-character name boundaries, malformed names/revisions/timestamps,
wrong JSON/root/field types (including boolean version), unsupported version,
unknown/missing/kind-inappropriate fields, invalid default, missing revision,
canonical symlink in place of managed material, and unreadable/invalid jars.
Missing registry must produce no filesystem mutation. Remove the external
file origin and prove the managed revision remains inspectable. Pin exact
list/inspect shapes, lexical source/domain ordering, default markers, and
secret-free malformed-input errors (review-checklist §1 and §3). Imports must
work without settings access or a browser dependency.

**Done when:** The reader either returns a fully validated snapshot and
specified safe metadata or a path-bearing operation error; it never rewrites
state, exposes cookie data, or hides corruption. New focused tests and
`just check` pass.

### P0003-C01-c — Locked host publication with failure and concurrency proof

**Build:**

- Add host writer primitives for initial empty-store publication, successful
  source publication/replacement, and default mutation, implementing *Named
  cookie sources* §1 and DEC-28. These are internal building blocks; D1's
  remaining migration/CLI work and D2's extraction/import operations call
  them later. Create managed directories at 0700 and publish registry,
  canonical material, and lock files at 0600. Do not chmod external origins.
- All mutations acquire the same exclusive advisory `.lock` and reread the
  current registry there. A publication carries the original source record
  (or expected absence); refuse a stale record rather than overwriting a
  competing refresh/replacement. Preserve unrelated source/default changes
  from the reread. Ordinary publication keeps the default; support deliberate
  source-and-default publication in one commit for later migration and the
  compatibility account switch (§1, §2, §5).
- Validate before committing; use a fresh opaque random revision and injected
  UTC refresh clock, serialize and sync the complete immutable copy first,
  then publish the complete registry atomically. Reuse `files.write_atomic`
  for same-directory publication and DEC-24/DEC-27 no-clobber semantics;
  never overwrite an existing canonical revision. Retain old revisions
  (DEC-31). A default-only change creates no revision or refresh timestamp.
- Keep the previous registry/referenced material intact on pre-commit failure;
  safe unreferenced revisions may remain after interruption. Preserve residue
  when ownership/removal cannot be established, and report cleanup errors
  per DEC-27 rather than promising impossible deletion (brief-checklist §6).
- Update README's implementation-status note/layout and planning status to
  identify the tested foundation, keeping public named-source commands and
  execution explicitly unimplemented (§5). Recipe behavior/menu text and
  the gate/CI definition do not change.

**Tests:** Drive create, replace, identical-content/new-revision, default-only,
and atomic source/default updates with synthetic records, deterministic IDs,
and time. Check 0700/0600 modes with a permissive umask, no external chmod,
no-clobber collision behavior, previous revision bytes retained, and unknown
default/stale publication rejection. Use independent processes and explicit
barriers to prove mutual exclusion, competing expected-absence publication,
one winner for two refreshes of the same record, and preservation of unrelated
source/default changes. Read while publishing and assert every observed
registry references complete parseable material. Inject failures in lock
acquisition, revision creation/write/sync, registry staging/sync/replacement,
and cleanup; compare previous committed bytes/material. Kill a controlled
writer after revision publication but before the registry commit, verify the
previous snapshot remains valid and a later writer acquires the released
lock. Account for allowed unreferenced revisions/reservations and failed
cleanup explicitly (DEC-27; brief-checklist §6). Failure doubles match real
exception attributes; reuse the existing atomic-writer tests instead of
copying that implementation (review-checklist §1–§2).

**Done when:** Readers observe complete old or new registry snapshots,
concurrent writers cannot silently overwrite a stale source, and no failed
pre-commit transaction changes previously referenced credentials/defaults.
Permissions, retention, default behavior, and bounded interruption residue
are pinned by tests; the full `just check` gate passes.

  redesign, downloader presets, VPN changes, and new gate/CI steps.

## Notes for the executor

- Suggested separation: a standard-library-only cookie parser/summary module,
  standard-library-only registry/reader module, and host writer module. Internal
  symbol names remain your choice; the registry paths/schema and public summary
  fields do not. Code cites DEC-28/DEC-30 where those rules are enforced.
- Avoid putting cookie values into dataclass reprs, captured library errors,
  assertions later echoed as product errors, or registry metadata. Library
  parsing diagnostics are not safe user-facing text.
- Existing `files.write_atomic` already implements the portable fallback and
  cleanup/error precedence. Its unit tests are the oracle if it is reused;
  any genuinely necessary second implementation needs parity tests against it.
- Do not document runnable commands this chunk does not expose; unit c's
  documentation records internal groundwork and the pending public surface.
- Before every unit commit, run `just check`, record `just check: green` in its
  commit body, and wait for existing CI runs to pass before the next unit push.
  Keep the branch history; the report names the three units and their evidence.
