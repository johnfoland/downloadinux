# Chunk P0002-C02 — Reliable cookie export and setup refresh

**Source:** project [P0002](../projects/P0002-stage1-followups.md), delivery
item D2 (all of it), resolving
[#20](https://github.com/johnfoland/downloadinux/issues/20) and
[#26](https://github.com/johnfoland/downloadinux/issues/26). Authority:
[target design](../target-design.md) *Migration* ("Cookie and user-agent
follow-ups, pinned for P0002"); DEC-25.

**Goal:** `just cookies` publishes a newly exported Firefox jar only after it
has proved that this run produced usable Netscape output, while the fixed
YouTube probe may fail without turning a successful export into a failure.
Every setup path also attempts the user-agent refresh exactly once. A failed
or malformed export preserves the previous managed jar, so routine refreshes
are safe to retry. The pull request closes issues #20 and #26.

## Kickoff notes

- The staged jar, not an existing final jar, is the only evidence that this
  export succeeded; keep it in `paths.cookies` so publication is one rename.
- The probe's status and the export's usability are separate: a valid staged
  header wins, including when yt-dlp exits nonzero and when it has zero rows.
- Keep yt-dlp diagnostics visible, but never print a cookie value. A missing or
  malformed staged jar must not reach the count or user-agent steps.
- Setup's existing-session branch adds the refresh; its export branch gets the
  one refresh from `just cookies` and must not add another.

## Units

### P0002-C02-a — Stage, validate, and publish the Firefox jar
**Build:**
- Rework `just cookies [profile]` per target design *Migration*, "Cookie and
  user-agent follow-ups, pinned for P0002" (DEC-25). Keep the configured
  directory at mode 0700, allocate a mode-0600 temporary in that same
  directory, and pass that path to yt-dlp's existing Firefox/profile export
  and fixed probe. Arrange cleanup from the moment the temporary exists.
- Capture yt-dlp's status without letting `set -e` stop validation, and stop
  suppressing its diagnostics. Treat the stage as usable only when its first
  line is the Netscape cookie-file header; zero cookie rows are valid.
- For a usable stage, atomically rename it over `cookies.txt`, keep the final
  mode 0600, print the existing site-count summary, and invoke
  `just useragent` exactly once. If yt-dlp was nonzero, also warn that the
  probe failed but the exported jar was published, and do not fail merely for
  that probe status. Other failures, including a failed user-agent command,
  retain their ordinary nonzero status.
- For an absent or unusable stage, exit nonzero after cleanup without changing
  the previous jar, printing counts, or invoking the user-agent. Preserve the
  profile argument and never print cookie values or contents.

**Tests:** Run the real `cookies` recipe against PATH stubs and temporary XDG
directories. Cover zero and nonzero yt-dlp statuses with a usable header,
including a header-only jar; assert publication, byte content, 0700/0600 modes,
visible diagnostics, the probe warning only on nonzero, the final summary, one
user-agent call, and no staged residue. Cover missing, empty, and wrong-header
stages with both a previous jar and no previous jar; assert nonzero, byte-for-byte
preservation where present, cleanup, no counts, no user-agent call, and no
cookie value in either output stream. Assert the stub receives the requested
Firefox profile and the temporary path rather than the final jar.

**Done when:** the staged header—not the probe exit—decides export success;
publication is one same-directory rename; every failure before publication
preserves the managed jar; modes, profile selection, diagnostics, counts,
cleanup, and secret-free output match DEC-25; and the focused tests plus
`just check` pass.

### P0002-C02-b — Refresh the user-agent on every setup path and document it
**Build:**
- In `just setup`'s existing-Instagram-session branch, run `just useragent`
  after reporting that cookies are left alone and before the build. Keep the
  export branch on `just cookies`, which owns its one refresh; do not add a
  second setup-level refresh there. Preserve the five setup steps, its
  continue-after-cookie-export-failure behavior, and DEC-21's successful
  warning when Chrome cannot be read.
- Update README.md *Step 3* and `cookies/README.md` to describe staged atomic
  replacement, preservation of the previous jar on an unusable export, the
  warning-and-success result when only the probe fails, and setup's refresh on
  both the existing-session and export paths. Keep the current manual-export
  guidance clearly distinct from the safer recipe behavior.

**Tests:** Execute the setup cookie step against stubs. With an existing
Instagram session, prove it skips the cookie export, invokes user-agent once
before the build, and keeps the jar unchanged. Without that session, prove it
invokes `just cookies` once and no separate `just useragent`, so unit a's
recipe supplies the sole refresh. Keep the existing assertions for all five
headings and for setup carrying on after a failed cookie export. Extend the
recipe-structure checks only where they pin this one-refresh ownership.

**Done when:** setup attempts exactly one user-agent refresh whether it keeps
the existing jar or exports one, never runs yt-dlp for an existing Instagram
session, preserves the five-step and failure-continuation behavior, and both
user documents accurately describe the accepted Stage 1 cookie workflow;
focused tests and `just check` pass.
